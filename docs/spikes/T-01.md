# T-01 — Spike: rrweb record cost on the terminal mock

**Status:** done · **Date:** 2026-11-03 · `@rrweb/record` **2.2.0** (pinned) · Chromium (Playwright 1.63) headless, 4 vCPU cloud VM

## Verdict
- rrweb is usable. The record chunk is **~23 KB min+gz**, against a 45 KB budget.
- The PRD's planned `data-rp-throttle` approach (filter rrweb's *output* in `emit`) **does not reduce main-thread cost**. It only halves bytes, because rrweb has already processed every mutation by the time `emit` runs.
- Replacement approach: a **MutationRecord prefilter hook** inside rrweb's `processMutations`, added through a small pinned patch to `@rrweb/record`. It drops text-only mutations inside `[data-rp-throttle]` containers before rrweb touches them, and the glue emits the latest value per node at most once per N ms. Result: per-batch main-thread time drops **4–9×** and bytes **~2× (≈6.5× for `textContent`-style updates)**.
- Found and patched an **rrweb bug**. `testableAccessors.Element` lists the methods `querySelector`/`querySelectorAll` as accessors, so rrweb always treats `Element` as tainted. It then creates a hidden iframe on every page and uses cross-realm accessors for every serialized node. Patching it cut the snapshot of a 3k-node DOM by ~19% at 4×.
- **Budget status:** snapshot and long-task budgets are met. **Per-batch time < 2 ms p95 at 4× is *not yet* met** on this mock (p95 ≈ 5 ms). It is met at 1× (p95 ≈ 1 ms). This is tracked as an open risk for T-20 and is not loosened (see "Open risk").

## Setup
- `sdk/bench/pages/terminal.html`: terminal mock. 3,074 elements / 5,760 nodes by default, with `?hist=60` giving the PRD's 3k-node size (2,785 nodes). It has a header, watchlist (40 symbols × 6 cells), order form with a password field, order book (2×20 levels), positions (30×10), history (235×8), and a same-origin chart iframe with canvases. The app consumes a Centrifugo-like WebSocket at **200 frames/s** (`sdk/bench/server.mjs`, newline-batched pushes) and repaints the UI at **10 Hz**: changed watchlist rows (5 cells) plus the whole order book (80 cells). That works out to **≈ 200 text mutations per tick, ≈ 2,000/s**. `?text=content` switches the app from `node.nodeValue = …` (Vue/React text binding → `characterData`) to `el.textContent = …` (→ `childList` swap).
- `sdk/bench/lib/spike-glue.js`: prototype replay chunk. It uses the PRD §4.6 record options, `emit` pushes into an array, the array is swapped and `postMessage`d every 500 ms, and a Worker does `JSON.stringify` + `CompressionStream('gzip')`.
- `sdk/bench/lib/build-spike.mjs`: bench-only build that instruments rrweb's `processMutations` with `performance.now()` and applies the two patches. It fails the build if a patch needle isn't found.
- **Per-batch cost** is the sum, per 500 ms window, of all rrweb mutation-callback time plus the glue flush. It is measured over 15 s after the snapshot settles, as the median of 3 runs. CPU is throttled through CDP `Emulation.setCPUThrottlingRate`.
- Run: `node sdk/bench/spikes/t01-rrweb-cost.mjs <seconds> <rate>` (`REPEAT=3`) and `node sdk/bench/spikes/t01-snapshot.mjs <rate> <runs>`. Raw results are in `t01-4x.json` / `t01-1x.json`.

Caveat: `performance.now()` is coarsened to 100 µs in non-isolated pages, and the VM is shared, so run-to-run noise is about ±20% (snapshot ±30%). Medians of repeats are reported.

## Findings
1. **Where the time goes:** rrweb's `processMutation` does per-record work: `isBlocked` + `needMaskingText` (two `closest()` walks), `textContent` reads, and mirror lookups, followed by `emit()` bookkeeping. At about 2,000 text mutations/s that costs roughly 15 ms per 500 ms at 4×. Filtering in `emit` can't recover it.
2. **Mutation hook:** a ~4-line patch in `MutationBuffer.processMutations` calls an optional `mutationHook(records) → records` before processing. The glue's hook:
   - `characterData` record whose parent is in a `[data-rp-throttle]` container: remember the Text node in a `Map` and drop the record.
   - `childList` record on a throttled element whose added/removed nodes are all Text and that has ≤ 1 child (a `textContent` swap): remember the parent and drop the record. The replay keeps the *original* text node id, and the flush emits text updates against that id.
   - Container lookup is cached per parent element in a `WeakMap`. Mask state is cached alongside, and masking of `.rr-mask`/`[data-rp-mask]` is honoured at flush. Blocked nodes are never in the mirror, so they're never emitted.
   - The same hook implements the **mutation guard**: more than 10,000 added nodes in one batch drops the batch and calls `takeFullSnapshot(true)`.
3. **Flush:** every 500 ms, the glue emits one synthetic rrweb mutation event (`texts` only) holding the latest values. With N > 500, nodes are staggered by `id mod N/500` so each 500 ms tick carries 1/k of the nodes, and every node is still emitted at most once per N ms. Ids are sent as a transferred `Int32Array` plus one `\u0000`-joined string, and the worker rebuilds the event. This was measured to be no slower than structured-cloning objects, with fewer allocations.
4. **rrweb mirror gotcha:** `removeNodeFromMap` doesn't clear `nodeMetaMap`, so `mirror.getId(node)` still returns an id after the node is removed. The glue must check `mirror.has(id)` / `getNode(id) === node` before emitting.
5. The remaining per-window cost is close to the floor for this design. It's dominated by reading each changed value once: on the order of 1 ms for about 280 changed nodes at 4×, plus first-read string materialisation and GC. A further ~1 ms comes from the hook loop over MutationRecords, which includes NodeList allocations for `addedNodes`/`removedNodes` in the `textContent` case.

## Decisions (→ PRD Decisions log D-04 … D-06)
- **D-04** `data-rp-throttle` is implemented as a MutationRecord prefilter through a pinned `@rrweb/record@2.2.0` patch (`pnpm.patchedDependencies`), not as an `emit` filter. It covers both `characterData` and single-text-child `childList` swaps, emits the latest value at most once per N ms per node, staggers across 500 ms ticks, and honours masking. The §4.6 mutation guard uses the same hook.
- **D-05** The same pinned patch fixes rrweb's `Element` taint-check bug (move `querySelector`/`querySelectorAll` from `testableAccessors` to `testableMethods`). It is also worth upstreaming to rrweb.
- **D-06** The README recommends `data-rp-throttle="1000"` on order-book / watchlist containers of trading terminals and `500` elsewhere. The PRD said `500`. This is a recommendation only: the attribute value is per-container and budgets are unchanged.

## Open risk (owner: T-20, verified again in T-51)
On this mock, the **< 2 ms p95 per 500 ms batch at 4×** budget is missed: p50 2.3–3.1 ms, p95 ≈ 5 ms. The mock may be heavier than real terminals (whole order book repainted 10×/s plus 5 cells per changed row), but the budget stays as written. Planned work in T-20:
1. Remove NodeList allocations from the hook (count added nodes only when `type === 'childList'`, and read each list once).
2. Cache `id` and mask per Text node at hook time so the flush avoids repeated lookups.
3. Move the throttled flush off the 500 ms batch tick into its own idle-aligned timer, so it doesn't stack with batch work in the same window.
4. Re-measure with the real SDK on this mock at 4×, plus on a lighter "watchlist-only" variant, and record both in `docs/bench.md`.

If p95 is still above 2 ms after that, I'll raise it with the owner rather than change the budget.
