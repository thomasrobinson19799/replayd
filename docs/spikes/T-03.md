# T-03 — Spike: CapacitorHttp + fetch/XHR patch

**Status:** done · **Date:** 2026-11-03 · **Verdict:** works with CapacitorHttp on and off, **but only with a constructor-level XHR wrapper when CapacitorHttp is on**. A conventional `XMLHttpRequest.prototype` patch silently stops capturing XHR after the first request.

## Method
No Android device or emulator is available in the build sandbox, so the spike runs the **real** Capacitor 8.6.0 `native-bridge.js` (copied from `@capacitor/android@8.6.0`, `capacitor/src/main/assets/native-bridge.js`) in Chromium. The Android host is emulated by `fake-android.js`:
- `window.androidBridge.postMessage` answers `CapacitorHttp.request` calls with a real HTTP request, the way the native OkHttp path does. HTTP errors resolve with their status, network errors reject.
- `CapacitorHttpAndroidInterface.isEnabled()` is toggled by `?caphttp=0|1`.
- `WEBVIEW_SERVER_URL = https://localhost`, as in the APK. The app's API is on another origin.
- Both scripts are injected at document start, which matches `WebViewCompat.addDocumentStartJavaScript` in `Bridge.java`.

The app (`t03.html`) makes 4 fetch and 3 XHR calls: GET 200, POST 500, 404, a relative URL, and a second XHR GET to detect prototype clobbering.

Run it with `node sdk/bench/spikes/t03/run.mjs` (exits non-zero if the planned approach fails).

## Results
| CapacitorHttp | Patch | Captured | Missing | Proxy URLs leaked | App unaffected |
|---|---|---|---|---|---|
| off | naive (prototype) | 7/7 | – | 0 | ✔ |
| off | planned | 7/7 | – | 0 | ✔ |
| **on** | **naive (prototype)** | **4/7** | XHR POST, both XHR GETs, 2nd POST | 0 | ✔ |
| on | planned | 7/7 | – | 0 | ✔ |

With CapacitorHttp on, the two POSTs went through the native bridge. GETs went through the bridge's `/_capacitor_http_interceptor_?u=` proxy URL. Since our wrapper is outermost, it always records the app's original URL.

## Findings (from reading `native-bridge.js` and confirmed by the run)
1. **Injection order is guaranteed.** The bridge is injected at document start (`addDocumentStartJavaScript`), or prepended into `<head>` by `JSInjector` on older WebViews. It runs before any app script, so the SDK always patches *after* the bridge and wraps its `fetch`/`XMLHttpRequest`. Nothing needs to wait or poll.
2. **The bridge's XHR breaks prototype patching.** `window.XMLHttpRequest` becomes a function that, on *every* construction, re-assigns `open`, `send`, `setRequestHeader`, `abort`, `getAllResponseHeaders` and `getResponseHeader` on the shared original `XMLHttpRequest.prototype`. Any prototype-level patch (Sentry-style `fill(XMLHttpRequest.prototype, 'open')`) is overwritten when the app creates its first XHR.
3. **The bridge's fetch** builds a `Response` from the native result (`new Response(data, {headers, status})`). `clone().text()` works and there is no streaming. JSON bodies are re-serialised by the bridge, so whitespace and key order can differ from the wire. `response.url` is an own property and is lost on `clone()`, so we take the URL from the request.
4. **Relative URLs, and URLs starting with the server URL (`https://localhost/…`), are never bridged.** They use the WebView's own fetch/XHR.
5. `xhr instanceof XMLHttpRequest` is already `false` under the bridge. Our wrapper keeps that behaviour (prototype and statics copied) and doesn't make it worse.
6. The bridge calls `console.time/timeEnd('CapacitorHttp …')` per request. The SDK doesn't patch `time`/`timeEnd`, so this doesn't show up as console noise.

## Decisions (→ PRD Decisions log D-07)
- **fetch:** always wrap the current `window.fetch` at `init()`. Under Capacitor that is the bridge's fetch.
- **XHR:** if `window.CapacitorWebXMLHttpRequest` exists and `window.XMLHttpRequest !== CapacitorWebXMLHttpRequest.fullObject` (the bridge is active), replace `window.XMLHttpRequest` with a constructor wrapper. It calls the bridge constructor, then installs **own-property** `open`/`send` wrappers on the instance, which shadow the prototype and survive re-assignment. Otherwise patch `XMLHttpRequest.prototype` as usual (web, and Capacitor with CapacitorHttp off). Cost: two closures per XHR instance, which is fine at XHR volume and adds nothing per message.
- **SDK transport must bypass CapacitorHttp.** The main thread uses `window.CapacitorWebFetch ?? originalFetch`, captured at `init()`. Going through the bridge would base64 the body across the JS↔native bridge, drop `keepalive`, and record our own ingest calls. The replay Worker's `fetch` is unaffected, because the bridge only runs in the window. The ingest URL is excluded from capture regardless.
- **Init order to document (README / Capacitor section):** Capacitor bridge (automatic) → app bundle → `@replayd/nuxt` client plugin → `init()`. No setting is needed in `capacitor.config` either way. `CapacitorHttp.enabled` may be true or false.

## Residual risk
The emulation can't prove WebView-specific behaviour, such as `DOCUMENT_START_SCRIPT` feature availability per WebView version, or real OkHttp header casing. That is covered by the real-device APK checklist in T-26 / T-51 (CapacitorHttp on and off).
