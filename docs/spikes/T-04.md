# T-04 — Spike: WP Rocket exclusion

**Status:** done · **Date:** 2026-11-03 · WP Rocket **v3.24** (GPL source, `github.com/wp-media/wp-rocket`, tag `v3.24`)

## Verdict
With **Delay JavaScript execution** enabled, the SDK runs before any user interaction as long as its `<script>` tag matches a `rocket_delay_js_exclusions` pattern. The excluded SDK also sees errors thrown later by scripts that WP Rocket delayed. Without the exclusion, the SDK doesn't run until the first interaction, and errors before that are lost. This matches the PRD's concern.

## Method
No licensed WP Rocket install is available, so the spike runs WP Rocket's **real code**:
1. `sdk/bench/spikes/t04/delayjs-harness.php` loads `inc/Engine/Optimization/DelayJS/HTML.php` (plus `RegexTrait`, `CommentTrait`) in `php:8.3-cli`. Options, DataManager and Logger are stubbed, and the shipped default `dynamic-lists.json` is used. It runs `delay_js()` and then the same runtime injection as `Subscriber::add_delay_js_script()`, which inlines `assets/js/lazyload-scripts.min.js` and the IE fallback into `<head>`.
2. `sdk/bench/spikes/t04/run.mjs` loads the transformed page in Chromium. It waits 2.5 s idle with no interaction, then moves the mouse and presses a key.

The test page has a jQuery-like head script, an inline config script, our SDK tag (`/_rp/sdk/1.0.0/replayd.min.js`, `defer`, `data-dsn`), a theme script that throws on `DOMContentLoaded`, and an analytics script that throws asynchronously.

## Results
| Variant | SDK tag after WP Rocket | SDK ran before interaction | Other scripts held until interaction | SDK saw errors of delayed scripts |
|---|---|---|---|---|
| default | `type="text/rocketlazyloadscript" data-rocket-src=…` | ✖ (never, until interaction) | ✔ | ✖ |
| exclusion `/_rp/sdk/` | unchanged | ✔ (at 18 ms; interaction at 2.5 s) | ✔ | ✔ (ReferenceError from theme, `analytics boom`) |

## Findings
1. `replace_scripts()` matches every exclusion as a **case-insensitive regex (`#…#i`) against the whole `<script …>…</script>` tag**, so a pattern can target the src path, an `id`, or a data attribute. `+`, `?ver` and `#` are escaped by WP Rocket. Other regex metacharacters are live, so patterns must be regex-safe.
2. Exclusions come from the dynamic default list, `delay_js_exclusions`, the safe-mode list, and finally the `rocket_delay_js_exclusions` filter. The filter is the documented extension point and the one the plugin will use.
3. Scripts with a non-JS `type` are never delayed, but a fake type would stop the browser executing our SDK, so the exclusion is the only correct approach.
4. Delay JS disables WP Rocket's "Load JS deferred" while it is active. Minify and combine are separate features with their own filters, and those must be excluded too (PRD §4.13).
5. Our tag needs no inline script: config goes in `data-*` attributes. This avoids `rocket_excluded_inline_js_content` / combine-inline issues completely.

## Decisions (→ PRD Decisions log D-08)
`replayd-wp` (T-41) registers:
- `rocket_delay_js_exclusions` → `'/_rp/sdk/'`, `'replayd-js'` (the handle id). This matches the tag even if the SDK base URL is changed.
- `rocket_exclude_js` (minify/combine of local files) → `'/_rp/sdk/(.*)'`
- `rocket_minify_excluded_external_js` → the ingest host, when the SDK is served from a different host
- `rocket_exclude_defer_js` → `'/_rp/sdk/(.*)'` (the tag already carries `defer`)

It also outputs the tag with `id="replayd-js"` and no inline script. The plugin's settings page shows a notice when WP Rocket is active, saying the exclusions were added automatically.

2026-11-06 requalification: `e2e/wordpress.e2e.mjs` now transforms the actual WordPress page through this public v3.24 engine, with exclusions read from the installed replayd plugin. Both the negative control and excluded variant passed: the control delays the SDK; exclusions preserve and execute it before interaction; other scripts remain delayed and are released after pointer/keyboard interaction. The existing five WordPress error/replay assertions and PHP plugin checks also pass. `WPROCKET_DIR` selects the public source checkout (defaults to `data/wp-rocket`). Without that source, the runner explicitly reports the Rocket checks as not run.

The transformed HTML is served by the local WordPress Apache container. A synthetic Playwright response lost Chrome's loopback address-space classification and caused a local-network CORS failure; using real HTTP fixes the fixture without weakening browser security.
